## 1. Product summary

Dotty is a web app where one person runs a team of AI bots inside an isometric 3D office.

- **Workspace and departments.** A **workspace** is one building, and each **department** is one floor.
- **Head bot.** It sits on the top floor and receives the user's tasks. It plans the work and delegates it.
- **Departments.** Each one has a **Lead bot** and **worker bots**. The Head and the Leads can assign tasks to any bot on any floor.
- **Where the user talks to bots.** In the web app (a side drawer), on **Telegram**, or on **Slack**.
- **When a bot is stuck.** It asks the user.
- **Approval rule.** **Nothing that sends, pays, publishes, deletes or merges happens without the user's approval.** This is enforced in code, not in prompts.
- **Schedules.** Bots run on routines. A **"while you slept" recap** arrives every morning.

### Success criteria (definition of done for v1)

Every journey in §3 works end to end in production. On top of that:

- Spend caps and task caps are enforced.
- No gated action can run without a recorded approval.
- The office shows a change in bot state within about 2 seconds.

### Version one includes

- Sign-up and sign-in, then creating a workspace (name and icon).
- The 3D office, in the style of `dotty-home.jpg`.
- A Head floor plus three starter departments:
  - **Assistant:** email, calendar and the daily brief.
  - **Research:** web browsing and price watching.
  - **Engineering:** coding in a sandbox and opening GitHub pull requests.
- Custom departments and custom bots that the user creates (name, what the bot does, tools). The Head bot can **propose** new bots and departments, and each proposal needs approval.
- A kanban board (**Boards**) showing every task.
- An inbox (**Waiting on me**) holding approvals and questions from bots.
- Chat with any bot in a side drawer.
- Routines (schedules) and the morning recap.
- **Telegram:** one shared Dotty bot. It handles chat, approvals and recap delivery.
- **Slack:** the user installs the Dotty Slack app. It handles chat, approvals and recap delivery, and gives bots a gated `slack.post_message` tool.
- The GitHub App, plus Engineering bots that code in Upstash Box.

### Not in version one

- A Content department template. Slack posting is a tool any bot can be given; there is no dedicated Content floor yet.
- Workspaces with more than one person. Users bringing their own API keys. Charging users for Dotty.
- The Voxel/Isometric style toggle shown in the mockup.
- A native mobile app.
- Vector or semantic memory.
- Tools written by users. Bots pick tools from a fixed catalogue.
- Tools that spend real money. The `pay` approval category exists in the gate, but no v1 tool uses it.

## 3. Core journeys

1. **Onboarding**
   1. The user signs up and creates a workspace (name and icon).
   2. A seed function builds the starter building: Head floor (Head bot), Assistant, Research and Engineering floors, each with a Lead and one worker.
   3. An optional checklist offers to connect Gmail and Calendar (Composio), Telegram, Slack and GitHub. Each step can be skipped.
   4. The user lands in the office and sends a first task to the Head bot.
2. **Delegation**
   1. The user sends a task to the Head bot, from the web, Telegram or Slack.
   2. The Head writes a plan and creates subtasks on the board.
   3. It assigns each subtask with `assign_task`.
   4. Each assigned bot starts a run, and its status updates live in the office: Working, Waiting or Resting.
3. **Approval**
   1. A bot calls a gated tool, and the gate creates an `inbox_items` row with a preview.
   2. The run pauses on a Trigger.dev waitpoint token.
   3. The user approves, edits or rejects the action in the web drawer, in Telegram (inline buttons) or in Slack (Block Kit buttons).
   4. The token is completed and the run resumes. On approval it carries out **only** the approved or edited payload.
4. **Stuck.** A bot calls `ask_user`, and a question item appears in Waiting on me. The user's answer completes the token and the bot carries on.
5. **Bot management**
   - The user creates a department, or a bot with a name, instructions and tools picked from the catalogue for its role.
   - The Head can call `propose_bot` or `propose_department`. That produces an approval item, and approving it creates the bot or department.
6. **Routines.** The user adds a schedule (cron expression and timezone) to a bot. Supabase Cron finds routines that are due and starts runs. Each run creates a task with `source = routine`.
7. **Recap.** At `recap_time` in the user's timezone, `generate-recap` summarises the overnight activity, tasks, approvals and spend. The recap is stored, shown in the app and sent to the connected channels.
8. **Engineering**
   1. A task is assigned to an Engineering bot.
   2. `engineering-run` creates an Upstash Box and clones the repo using a GitHub App installation token.
   3. The agent makes its changes and runs the tests, then pushes a branch.
   4. The run opens a **draft** pull request.
   5. The bot asks to merge, which is a gated `merge` approval.
   6. Once approved, the pull request is merged through the GitHub App.

### Failure states

| Situation | Behaviour |
|---|---|
| A connection has expired or been revoked (Composio, Slack, GitHub) | The tool returns `needs_reconnect`, a question item appears asking the user to reconnect, and the task moves to `waiting_on_me`. |
| The daily spend cap is reached | Every new step or run is refused, the bot status becomes `resting`, a banner shows in the office, and the task stays in `doing`. Runs resume once the cap is reset or raised. |
| The daily task cap is reached | `assign_task` and new task creation are refused with an explanation, and the Head tells the user. |
| A run fails after retries | The task becomes `failed`, the error appears in the activity feed, and the task card has a **Retry** button. |
| An approval is not answered within 72 hours | The token times out, the item becomes `expired`, and the bot treats the action as rejected. |
| Delegation goes deeper than 3 levels | `assign_task` refuses and the bot must do the work itself or ask the user. |

## 4. Architecture

```
Browser (Next.js 16 app, R3F office)
   │  server actions / route handlers           ▲ Supabase Realtime (bots, tasks, activity, inbox_items)
   ▼                                            │
Next.js on Vercel ──── Supabase (Auth, Postgres+RLS, Realtime, Cron, Vault)
   │  tasks.trigger / wait.completeToken        ▲ service-role writes
   ▼                                            │
Trigger.dev tasks: bot-run · engineering-run · dispatch-routines · generate-recap
   │
   ├── AI SDK + Claude (tool loop)
   ├── Composio (Gmail, Google Calendar)
   ├── Browserbase + Stagehand (browse, extract, price checks)
   ├── Upstash Box (code sandbox)
   ├── GitHub App (installation tokens, PRs, merge)
   └── Chat SDK adapters: Telegram (shared bot), Slack (per-install)
```

### What each part is responsible for

- **Next.js (Vercel)**
  - The user interface.
  - Server actions for every write the user makes.
  - Webhooks: `/api/webhooks/telegram`, `/api/webhooks/slack`, `/api/webhooks/github`, `/api/connect/composio/callback`.
  - `/api/cron/tick`, which Supabase Cron calls and which is protected by `CRON_SECRET`.
  - `/api/chat/[botId]`, which streams chat replies in the drawer.
  - Server actions that decide inbox items and call `wait.completeToken`.
  - Never runs long agent loops.
- **Supabase**
  - Auth.
  - Postgres with row-level security on every table.
  - Realtime `postgres_changes` filtered by `workspace_id`.
  - `pg_cron` and `pg_net`: post to `/api/cron/tick` every minute.
  - Vault, for encrypted Slack bot tokens.
- **Trigger.dev**
  - Every agent run. Runs have no serverless time limit and retry automatically.
  - Waitpoint tokens, used for both approvals and questions.
  - A concurrency key per workspace (`workspaceId`), so one workspace can't starve the others.
  - The Trigger.dev dashboard is the main place to observe runs.

### Agent runtime (`trigger/bot-run.ts`)

1. **Load context:** the bot, its task, its notes, the last N messages and activity for the task, and the department's tools.
2. **Check caps** (spend and tasks). If a cap is exceeded, stop and set the bot to `resting`.
3. **Run the loop:** call AI SDK `generateText` with the bot's tools from the catalogue. Use `stopWhen: stepCountIs(25)`, and recheck spend before each step with `prepareStep`.
4. **Record each step:** insert rows into `activity` and add the token cost to `runs.cost_cents`.
5. **Finish:** write the task result, set the task status, set the bot status, and append to the bot's notes when the bot decides to.

### Tool catalogue and the approval gate (`lib/agents/tools/`)

Every tool is declared once with metadata:

```ts
type ToolDef = {
  key: string;                 // "gmail.send"
  department: "core" | "assistant" | "research" | "engineering" | "slack";
  roles: Array<"head" | "lead" | "worker">;
  risk: "read" | "write" | "gated";
  action?: "send" | "pay" | "publish" | "delete" | "merge" | "create_bot" | "create_department";
  preview?: (input) => InboxPreview;     // what the user sees before approving
  execute: (input, ctx) => Promise<Result>;
};
```

`buildTools(bot, ctx)` turns the bot's `tool_keys` into AI SDK tools.

**How a gated tool runs** (`gate.ts`):

1. Insert `inbox_items` (kind `approval`) with the preview.
2. Call `wait.createToken({ timeout: "72h", tags: [workspaceId] })` and store `waitpoint_token_id`.
3. Set the task to `waiting_on_me` and the bot to `waiting`.
4. Pause on `wait.forToken`.
5. When the token completes:
   - **Approved:** run `execute` with `edited_payload ?? input`.
   - **Rejected or expired:** return a refusal to the model.

**Gate invariants:**

- The model never receives a handle that bypasses the gate.
- `execute` for a gated tool takes an `approvalId` and checks that the matching `inbox_items` row is `approved` before acting.
- Unit tests cover both invariants.

### Chat (drawer, Telegram, Slack)

- **Drawer.** `/api/chat/[botId]` uses AI SDK `streamText` with a limited tool set: `notes.read`, reading task and board status, `create_task` (for this bot, or for the Head) and `answer_inbox_item`. Anything that needs real work becomes a task run by `bot-run`. This keeps chat fast and stops gated work from running inside a request.
- **Telegram and Slack.** These go through Vercel Chat SDK adapters and share the same handler as the drawer (`lib/chat/handle-message.ts`), without streaming.
  - **Routing.** A message goes to the Head bot unless it starts with `@BotName`.
  - **Approvals.** These are sent as inline buttons in Telegram and Block Kit buttons in Slack. Each callback checks the sender against the linked user, then calls the same decide action used on the web.
- **Linking Telegram.** A link code is created in the app. The user opens `t.me/<DottyBot>?start=<code>`, and the webhook binds the `chat_id` to the user.
- **Linking Slack.** The user clicks "Add to Slack" (OAuth v2) and the installation is stored in `connections`. The bot token goes into Vault. Messages are accepted only from the Slack user who installed the app.

### Scheduling and recap

- **Every minute,** `pg_cron` posts to `/api/cron/tick`. The route:
  1. Claims due routines with `UPDATE … SET next_run_at = <next> WHERE next_run_at <= now() RETURNING *` (claimed once, so no routine runs twice).
  2. Triggers `bot-run` for each claimed routine.
  3. Triggers `generate-recap` for each workspace whose local `recap_time` has just arrived and has no recap for today yet.
- **Daily caps** are reset by deriving spend from `runs` for the current local day. No reset job is needed.
- **`generate-recap`** gathers what happened since the previous recap and summarises it with Haiku. It then stores a `recaps` row, logs an `activity` row, and sends the recap to Telegram and Slack.

### 3D office (`components/office/`)

- **Scene.** React Three Fiber with drei:
  - An `OrthographicCamera` at a true isometric angle.
  - `MapControls` limited to pan and zoom.
  - Floors stacked with vertical gaps, in the order given by `departments.floor_index`.
- **Floor.** Glass walls, floor slab, a coloured accent for the department, a label sign, and desks laid out in a grid.
- **Desk props.** Low-poly instanced plants, servers, safes and monitors.
- **Robot.**
  - Procedural low-poly geometry: rounded head box, visor face, antenna, body.
  - The bot's `avatar` field (`{ color, accessory, seed }`) sets its colour and its accessory: headset, glasses, cap or none.
  - Idle bob and typing animations.
- **Status ring.**

  | Status | Ring |
  |---|---|
  | `working` | Blue |
  | `waiting` | Amber, pulsing |
  | `resting` | Grey |
  | `error` | Red |

- **Speech bubble.** An icon shows the bot's current activity type (mail, chart, laptop).
- **Interaction.** Clicking a bot selects it and opens the drawer; hovering shows a tooltip.
- **2D portraits.** `RobotPortrait` renders the same robot parameters in a small canvas, or a cached PNG snapshot, for the team panel, drawer header and board cards.
- **Performance.**
  - Instanced props.
  - `frameloop="demand"` unless something is animating.
  - Under 150 draw calls for a 6-floor building.
  - `prefers-reduced-motion` turns off the bobbing.
- **Fallback.** On narrow screens (< 768px), when there's no WebGL, or when the user asks for it, show a list view of floors and bots with the same data.

## 5. Data model

All tables live in `public`. Each has `id uuid pk default gen_random_uuid()` and `created_at timestamptz default now()`. Every table except `profiles` has `workspace_id uuid not null references workspaces on delete cascade`.

| Table | Columns (beyond id / workspace_id / created_at) |
|---|---|
| `profiles` | `user_id uuid pk → auth.users`, `display_name`, `timezone text default 'UTC'` |
| `workspaces` | `owner_id → auth.users`, `name`, `icon text`, `daily_spend_cap_cents int default 500`, `daily_task_cap int default 50`, `recap_time time default '07:00'` |
| `departments` | `name`, `kind enum(head, assistant, research, engineering, custom)`, `floor_index int`, `color text`, `unique(workspace_id, floor_index)` |
| `bots` | `department_id`, `role enum(head, lead, worker)`, `name`, `instructions text`, `tool_keys text[]`, `model text`, `avatar jsonb`, `status enum(working, waiting, resting, error) default 'resting'`, `status_detail text`, `last_active_at`, `created_by enum(user, bot)` |
| `tasks` | `title`, `body`, `status enum(backlog, doing, waiting_on_me, done, failed, cancelled)`, `assignee_bot_id`, `created_by_bot_id null`, `parent_task_id null`, `depth int default 0`, `source enum(web, telegram, slack, routine, bot)`, `result jsonb`, `position float` (kanban order) |
| `runs` | `task_id`, `bot_id`, `trigger_run_id`, `status enum(queued, running, waiting, completed, failed)`, `input_tokens`, `output_tokens`, `cost_cents numeric`, `started_at`, `ended_at`, `error text` |
| `activity` | `bot_id null`, `task_id null`, `type text`, `summary text`, `payload jsonb` |
| `inbox_items` | `bot_id`, `task_id`, `run_id`, `kind enum(approval, question)`, `action enum(send, pay, publish, delete, merge, create_bot, create_department) null`, `tool_key`, `preview jsonb`, `input jsonb`, `edited_payload jsonb null`, `answer text null`, `status enum(pending, approved, rejected, answered, expired)`, `waitpoint_token_id`, `decided_via enum(web, telegram, slack) null`, `decided_at` |
| `messages` | `bot_id`, `role enum(user, assistant, system)`, `parts jsonb`, `channel enum(web, telegram, slack)` |
| `bot_notes` | `bot_id unique`, `content text`, `updated_at` |
| `routines` | `bot_id`, `name`, `cron text`, `timezone text`, `prompt text`, `enabled bool`, `next_run_at timestamptz` (indexed where enabled) |
| `watches` | `bot_id`, `url`, `target text` (what to read), `last_value numeric`, `threshold numeric null`, `last_checked_at` |
| `recaps` | `for_date date`, `content jsonb`, `unique(workspace_id, for_date)` |
| `connections` | `provider enum(composio_gmail, composio_calendar, github, telegram, slack)`, `external_id`, `meta jsonb` (installation_id, repos, team_id, chat_id), `vault_secret_id null`, `status enum(active, needs_reconnect)` |
| `telegram_link_codes` | `code text pk`, `user_id`, `expires_at` |

**Row-level security**

- Every table has row-level security enabled. Policy for workspace-scoped tables:
  ```sql
  using (exists (select 1 from workspaces w where w.id = workspace_id and w.owner_id = auth.uid()))
  ```
- `profiles`: `user_id = auth.uid()`.
- The Trigger.dev tasks and the webhooks use a **service-role** client wrapped by `adminForWorkspace(workspaceId)`, which always filters by `workspace_id`.
- `inbox_items.status` can only change through the server decide action, never by a client update. Row-level security allows `select` only.

**Realtime publication:** `bots`, `tasks`, `activity`, `inbox_items`.

**Seeding:** the `public.create_workspace(name, icon)` RPC (SECURITY INVOKER, one transaction) creates the workspace, its four starter departments and seven bots. The schema lives in `supabase/migrations/20261110125607_init_schema.sql`. That file also caps each account at 10 workspaces, and uses composite foreign keys so a child row always stays in its parent's workspace.

## 11. Self-hosted migration proposal (2026-11-20)

- **Status:** Confirmed by the user (2026-11-20). Replaces the v1 infrastructure stack.
- **Constraint set by the user:** one self-hosted Postgres database, one DeepSeek API key, a low-spec server (2 cores, 3.4 GiB RAM). No Supabase, no Trigger.dev, no Upstash Box. Engineering runs in rootless Podman; login is email/password; research tools stay enabled; Caddy serves TLS.

### Target architecture

```
Browser (Next.js 16, R3F office, React Query polling)
   │  server actions / route handlers
   ▼
    Caddy (HTTPS + reverse proxy)
   │
Next.js on the user's server ──── self-hosted Postgres (data + chat state + job queue)
   │  boss.send / job handlers                     ▲
   ▼                                               │
pg-boss worker (bot-run, routines, recaps) ────────┘
   │
   ├── AI SDK + @ai-sdk/deepseek (DeepSeek API)
   ├── SearXNG (self-hosted search, JSON API)
   ├── rootless Podman (per-run code sandbox for Engineering)
   └── optional: Chat SDK (Telegram/Slack), GitHub App
```

Everything except the model API runs on the user's server. Optional external services stay optional (Composio, GitHub, Telegram, Slack).

### Decisions that supersede v1 decisions

| # | New decision |
|---|---|
| D10' | Background runs use **pg-boss** on the self-hosted Postgres, replacing Trigger.dev. A separate systemd worker process runs job handlers. Approval waits keep the job active while the worker heartbeats, and poll the `inbox_items` row every 2 seconds for up to 72 hours; the UI decision writes the database row that releases the waiter. |
| D14' | The model provider is **DeepSeek** through `@ai-sdk/deepseek` (`DEEPSEEK_API_KEY`), replacing Vercel AI Gateway and Claude. Model tiers map: sonnet → `deepseek-chat`, haiku → `deepseek-chat`, opus → `deepseek-reasoner`. The model picker labels change accordingly. `lib/ai/cost.ts` price tables switch to DeepSeek prices (verify current prices before shipping). |
| D16' | Composio is removed from the default configuration. Gmail/Calendar/Notion tools stay in the code but are hidden when `COMPOSIO_API_KEY` is absent. The Assistant floor keeps only core tools in this configuration. |
| D20' | Upstash Box is replaced by **rootless Podman**. Each code run gets a disposable container: the host clones the repo with the read-only GitHub token, bind-mounts the workspace, and runs the container with `--network=none`, memory/CPU/PIDs limits and a tmpfs workspace overlay, so no credential ever enters the container. Prebuilt base images per runtime (node, python, go, rust, ruby) are maintained as Containerfiles. GitHub read tools remain optional behind the GitHub App. |
| D21' | Research tools are enabled without Browserbase or Composio: `web.search` calls a self-hosted **SearXNG** JSON API; `browser.extract` uses server-side fetch plus Readability with SSRF guards (block private ranges). Price watches keep working on top of `browser.extract`. |
| D22' | **SMTP email sending is a per-Bot tool, not a Composio app.** A new `email.send` tool uses Nodemailer with server-side SMTP settings. Every role can select it in Bot settings, but no Bot is enabled automatically. The tool supports plain-text `to`/`cc`/`bcc`/`subject`/`text`, cannot send from chat, and always pauses on an editable approval card in a background run before calling SMTP. The full contract is in `docs/superpowers/specs/2026-11-20-smtp-email-design.md`. |
| A2' | The app is deployed to the user's own server (systemd + **Caddy** for automatic HTTPS and reverse proxy), not Vercel. |
| Realtime | Supabase Realtime is removed. PostgreSQL triggers publish small change metadata with `pg_notify`; `/api/events` fans it out over SSE to the signed-in workspace. Chat messages merge by ID so an older server snapshot never replaces a just-finished streamed reply. Polling remains only as a fallback (15 s busy, 60 s idle). |
| Auth | **Better Auth** replaces Supabase Auth. **Email/password** is the login method, with email verification disabled (no SMTP needed). Magic link and Google OAuth can be added later if an SMTP / OAuth provider appears. |
| Data access | **Drizzle ORM + `pg`** replaces `supabase-js`. A shared query layer (`lib/db/`) enforces workspace ownership in application code, replacing RLS policies. |

### Assumptions and remaining operational items

1. Research assumes a self-hosted SearXNG instance; a managed API (Tavily, etc.) is a drop-in swap for the `web.search` implementation.
2. Podman runs rootless under a dedicated system user; container images per runtime add disk usage (a few GB in total).
3. DeepSeek API prices and tool-calling limits must be verified before the spend tables are finalised.
4. A domain is required for Caddy's automatic TLS; the domain name will be filled into `NEXT_PUBLIC_SITE_URL`.
